# Run the agents in one isolated OrbStack machine

The agent stack (Hermes Agent as the front door — LAN dashboard, Telegram gateway; OpenCode as the coding agent it hands work to) runs in **one** isolated OrbStack machine named `agents` (Ubuntu 24.04, ARM64), provisioned by the opt-in `playbooks/agents-vm.yml`. Not two machines (one per agent), not a container, and no longer on the Mac itself — Hermes was an opt-in app in this repo's Mac setup until it moved entirely into the VM.

One machine because the two agents are one system: Hermes delegates coding work to OpenCode through a loopback-only server inside the same machine (the `opencode-bridge` skill runs `opencode run --server http://127.0.0.1:4096`), and both operate on the same shared workspace (`~/agent_workspaces` mounted in as `/workspace`, with clones of the personal repos). Splitting them across machines would force that bridge traffic and those files over a network for no benefit. An isolated OrbStack machine (not Docker) because the agents are long-lived, service-owning workloads — systemd units for the OpenCode server and both Hermes services need a real OS, and OrbStack gives each machine its own mount list, an SSH alias (`ssh <name>@orb`, user = machine name) that Ansible can drive, and a per-machine LAN exposure setting.

## Consequences

- **The machine is isolated by default and exposed exactly where intended.** `orb create --isolated` NATs it behind the Mac (no IP of its own); only `~/agent_workspaces` is shared in. LAN access to the dashboard (`<mac-ip>:9119`) comes from OrbStack's `machines.expose_ports_to_lan` — pinned on by the playbook so a manual UI change is healed. The OpenCode server never crosses that boundary: loopback only, behind nothing, reachable solely from inside the VM. The dashboard is the one service with a network-facing door, and it sits behind username/password basic auth (Hermes requires authentication for non-loopback binds); the signing secret is generated once and kept stable, so dashboard sessions survive reboots.
- **The ceilings are OrbStack-wide.** `orb config set memory_mib`/`cpu` bound every machine on the Mac, not just `agents`, so the playbook treats 12 GiB / 6 cores as a global setting on this 32 GB machine and reconciles it (a no-op when unchanged). A runaway process in either agent shares the same headroom; that is accepted rather than adding per-service cgroups.
- **The VM's login user doubles as the service user.** OrbStack convention makes the SSH user equal to the machine name; systemd units run as that user and only system-level tasks (apt, `dpkg -i`, unit files, systemctl) use become. No extra unprivileged user is created.
- **Re-running is the update path, and it never recreates** (ADR-0001's rule extended to machines): an existing machine is kept and reconciled (mounts, ceilings), the gh login runs only when not logged in or no token yet, clones and installs are presence-gated. To rotate the GitHub PAT: delete `~/.config/gh` in the VM and re-run.
- **Secrets are one vault file, feature-gated.** Only `anthropic_api_key` and `hermes_dashboard_password` are required; Telegram, the Google OAuth client (read-only Gmail/Calendar via `workspace-mcp`, stdio-spawned by Hermes), the GitHub PAT and the oMLX key each enable their feature only when filled in. The Google client secret lands in Hermes' `config.yaml` (0600, fully playbook-owned); the oMLX provider is omitted from both agents' configs until `local_llm_models` lists real model IDs (the server requires a key — probe it and fill both).
- **OrbStack itself is installed or updated only on "yes".** It was taken out of the Mac baseline (`site.yml`): answering yes to bootstrap's agents-VM question brings in the hypervisor too — absent → `brew install --cask orbstack`; brew-managed and outdated → scoped upgrade; installed by hand → left entirely alone (ADR 0001 extended to the hypervisor). A "no" touches neither OrbStack nor an existing machine, and a "yes" without the secrets file stops before any of it.
- **The playbook has two halves** (Mac side, then Linux side through the SSH alias) so each can be tested offline against stubs; bootstrap's agents-VM question — pre-answerable via `PROVISION_AGENTS_VM` for automation, default No, no terminal → No — runs it after the site playbook, never by default; the vault password comes from `AGENTS_VAULT_PASSWORD_FILE` or is asked interactively (`--ask-vault-pass`).
